# 5 cm 越阶状态机检查点

日期：2026-08-29

## 目的

把当前已经验证过的整机 MuJoCo 动力学模型，接上一套最小、可解释、由接触事件驱动的
越阶动作控制器。这个检查点只验证控制链路和失败判定，不宣称真实机器人已经具备
越阶能力。

## 上游证据校准

在上游固定提交 `e2444395dd3a76c20b0683fbb1e123c21186a502` 的
`esp32-controller/software/src/main.cpp` 中，正常控制任务明确包含离地逻辑：
离地时关闭两个轮端电机，把腿长目标切换到 `0.12 m`；重新触地后进入缓冲，
并在腿长压缩回来后恢复正常控制。这证明遥想星空原控制器确实考虑了弹跳/离地
过程，也说明本仓库最初的“空中收腿并继续驱动车轮”并不是正确的上游复现。

但上游 README 和代码没有给出“5 cm 台阶成功”的可重复定量实验记录；因此
“原机器人能跳”与“原机器人已证明通过 5 cm 台阶”仍是两个不同结论。

## 控制阶段

```text
APPROACH → CROUCH → PUSH → FLIGHT → LANDING → RECOVER
```

- `APPROACH`：轮端扭矩让底盘向台阶接近，直到检测到轮-台阶接触。
- `CROUCH`：腿长目标从 90 mm 收到约 70 mm。
- `PUSH`：腿长目标伸到约 120 mm，并通过现有 Jacobian 施加虚拟腿轴向蹬伸力。
- `FLIGHT`：检测轮子离开地面后关闭轮端，并把腿长保持在约 120 mm。
- `LANDING`：检测重新接触地面或台阶，保持 120 mm 作为缓冲，再等待腿长压缩。
- `RECOVER`：恢复 90 mm，并要求两轮均在台阶高度以上、俯仰受限且垂直速度较小。

“台阶顶面”判定使用轮心高度 `h_step + r_wheel` 附近的几何条件，而不是只要轮子
碰到台阶就算成功。这样可以区分台阶立面碰撞、轮缘接触和真正的顶面支撑。

阶段切换使用 MuJoCo 接触、轮轴位置、腿长、底盘速度和俯仰测量；没有直接修改底盘
位姿，也没有播放固定动画。

## 2.5 kg / 5 cm 结果

运行：

```bash
python3 scripts/validate_stair_controller.py --mass 2.5 --height-cm 5
```

结果：

- 经过 `APPROACH`、`CROUCH`、`PUSH`、`FLIGHT`、`LANDING`、`RECOVER`；
- 状态始终为有限数值；
- EL05 命令没有超过 ±6 N·m，轮端命令没有超过 ±0.3 N·m；
- 最终在 `RECOVER` 失败，原因是没有建立稳定的双轮台阶顶面接触。

因此当前结论是：

**控制器已接入真实接触模型，台阶接触和阶段判定链路有效；5 cm 越阶尚未成功。**

当前失败还暴露出落地后姿态恢复不足的问题。现在控制器已按上游逻辑修正为空中
关闭轮端、腿长保持在 120 mm 并使用落地缓冲；下一步应优先解决台阶立面接触后
的前向速度/接触几何，而不是修改五连杆杆长或把 EL05 扭矩先验地判成不足。

## 参数矩阵

`scripts/sweep_stair_controller.py` 已对 2.0、2.3、2.5 kg 和 5、10、15 cm 组合
执行相同控制器。当前九个组合均观察到台阶接触，但均未建立稳定双轮顶面支撑，
因此全部为 `FAILED`。质量变化没有改变当前主要失败模式；主要限制是单级台阶接触
后的翻越/支撑，而不是 Python 数值稳定性。

## 证据边界

这是 MuJoCo 简化模型中的控制器检查。它不证明 CAD 无干涉、执行器真实峰值能力、
摩擦系数准确性或实物越阶可靠性。

## 模型验证修正

本次检查补充了按高度静态编译的台阶模型：
`robot_dynamic_*kg_step_{5,10,15}cm.xml`。此前仅在已经编译的 MuJoCo 模型上修改
`geom_size`，会导致显示高度与碰撞常量不一致；现在越阶脚本直接加载对应高度的模型。
这修正了验证输入，但没有把当前失败改写成成功：2.5 kg / 5 cm 仍未形成稳定的
双轮顶面支撑，状态机结果仍为 `FAILED`。
